PROJECT 01 / LLM OBSERVABILITY · DEVELOPER TOOLING

LLM Inference Logging

A provider-agnostic TypeScript SDK and dashboard for understanding LLM requests. It captures latency, token usage, errors, and redacted previews, with PostgreSQL-backed event storage and a Redis/BullMQ worker for asynchronous ingestion. A streaming chat interface demonstrates the instrumentation end to end.

Explore the code ↗

The problem

When an application calls multiple LLM providers, debugging becomes fragmented. Request latency, token usage, and failures need a consistent representation without coupling the application to one provider’s logging format.

Inside the build

  • Instrument at a reusable boundary. A wrapper-first TypeScript SDK captures normalized inference events. Optional fetch and provider-client instrumentation offer integration paths for existing applications.
  • Separate inference from telemetry processing. The ingestion service persists an event in PostgreSQL before publishing its identifier to a Redis/BullMQ queue. A separate worker materializes queryable logs and reconciles pending outbox entries.
  • Make the system explorable. A reference Next.js application provides streaming chat and a dashboard for latency, throughput, failures, and provider usage. A mock provider exercises the pipeline without an external model key.

Scope & trade-offs

This is a prototype for a trusted environment. Authentication and tenant isolation are not implemented. Redaction is a best-effort layer on telemetry previews; full chat messages remain stored without redaction. Cancellation currently uses an in-memory registry, which constrains the application to one active replica.

What I’d explore next

Externalize cancellation state, add tenant boundaries, and introduce dead-letter handling and bounded reconciliation retries.
