PROJECT 04 / PAYMENT SYSTEMS · DEVNET PROTOTYPE

MerchantPay

A merchant payment prototype focused on reliable accounting. A Go API manages idempotent payment intents, verifies finalized Solana devnet transfers, and records balanced ledger entries for reconciliation. A TypeScript checkout provides payment QR codes while signing remains in the user’s external wallet.

Explore the code ↗

The problem

A payment interface needs more than a success message. It needs consistent state transitions, protection against duplicate events, exact amounts, and accounting records that can be reconciled with settlement.

Inside the build

  • Represent money exactly. Amounts use integer atomic token units across the checkout, API, transaction verification, and ledger rather than floating-point values.
  • Verify before crediting. The backend checks transaction finality, recipient, token mint, and the credited amount through Solana RPC before recording a successful payment.
  • Make retries and accounting explicit. Idempotency keys protect repeated operations. PostgreSQL transactions coordinate payment updates and balanced ledger entries, while reconciliation reports highlight inconsistencies.

Scope & trade-offs

MerchantPay is a portfolio prototype for Solana devnet test tokens. Signing happens in an external wallet, and the application does not receive private keys. It is not presented as a service for real-money payments.

What I’d explore next

Extend adversarial event and reconciliation tests, strengthen access control, and document operational procedures for delayed or unavailable RPC responses.
